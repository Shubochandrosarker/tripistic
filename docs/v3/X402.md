# x402 — machine payments for agent routes

## Status

Implemented, and **off by default**.

Two API routes accept payment from autonomous agents. Nothing else in Tripistic
is affected: no booking, refund, payout or Stripe path touches any of this, and
an integration test asserts that a verified x402 payment writes no row to the
booking payment tables. Conflating the two would put an experimental settlement
rail in front of the revenue that pays the bills.

## The flow

```
agent → POST /api/agent/travel-search        (no token)
      ← 402 + X-Payment-Required { amount, currency, network, payTo, verifyUrl }

agent settles on-chain

agent → POST /api/agent/x402/verify          { transactionReference, network, … }
      ← { token, expiresAt, maxUses }

agent → POST /api/agent/travel-search        Authorization: Bearer <token>
      ← 200
```

The 402 response *is* the interface. An agent reads it and settles without a
human ever seeing a checkout page, which is the whole reason the scheme exists.

## Priced routes

An explicit allow-list in `lib/x402/config.ts`, never a prefix match — a prefix
would silently start charging for anything added underneath it, and the first
sign would be an integration breaking on a 402 nobody meant to introduce.

| Route | Price | Access window | Calls |
|---|---|---|---|
| `POST /api/agent/travel-search` | 0.01 USDC | 60 min | 50 |
| `POST /api/agent/itinerary` | 0.05 USDC | 60 min | 10 |

`travel-search` returns the same publicly listed tours a storefront shows; what
the price buys is the structured, paginated, no-scraping version and the rate
ceiling a grant carries. `itinerary` costs more because it runs a model, over
candidate tours fetched first and passed into the prompt — so the model arranges
real inventory rather than inventing it.

## Safety

**Two keys for real funds.** `X402_ENABLED=true` turns the rail on;
a mainnet `X402_NETWORK` additionally requires `X402_ALLOW_MAINNET=true`. One
variable copied between environments must not be enough to start accepting
money on experimental code.

**Disabled looks absent.** With x402 off the protected routes answer 404, not
503. A switched-off experimental rail should not advertise a switch to probe at.

**Tripistic never decides that a payment happened.** A settlement facilitator
does; `lib/x402/verify.ts` asks it, records the answer, and refuses to credit
the same settlement twice.

**Replay is prevented by the database, not by application logic.** The unique
index on `X402Payment.transactionReference` is the defence, and the payment row
is claimed *before* the facilitator is called — verifying first would leave a
window in which two concurrent submissions both verify. The loser of the race
never reaches the facilitator at all.

**Grant tokens are returned once.** Only a SHA-256 is stored, so a leaked
`x402_access_grants` table is a list of hashes rather than working credentials.
Redemption is a conditional `UPDATE`, so two concurrent calls cannot both spend
a grant's last use.

**Grants are route-scoped.** A token bought for the cheap search route does not
open the expensive itinerary route; without that check the price list would be
advisory.

**Every rejection returns the same 402.** Distinguishing "expired" from "never
existed" would tell a caller probing tokens which guesses were once valid, and a
paying agent's correct action is identical in both cases.

## Configuration

```bash
X402_ENABLED=false
X402_NETWORK=base-sepolia   # testnet default
X402_PAY_TO=                # platform wallet
X402_FACILITATOR_URL=
X402_ALLOW_MAINNET=false    # second key, required for a mainnet network
```

`x402Readiness()` returns the *reason* it is not ready, not just a boolean, and
the admin screen shows it. "Not ready" with no explanation costs an afternoon.

## Admin

`/admin/commerce/x402` — readiness and its reason, verified and rejected
payments, revenue by route, active grants, and the price list as the server
actually resolves it. Payer addresses are truncated: a wallet address links
every payment the same agent ever made, here and elsewhere, so a support
screenshot should not become a correlation key.

## Known limitations

- **No facilitator has been exercised against a live testnet in this
  environment.** `verifyPayment` is covered by integration tests through an
  injected client — accept, reject, unreachable, replay and concurrency all
  pass — but the HTTP shape of `httpFacilitator` is written to the documented
  contract and has not been confirmed against a running facilitator. Do that on
  staging before enabling anywhere.
- **No settlement is ever initiated by Tripistic.** The agent pays; we verify.
- **Grants are not revocable from the admin UI.** Expiry and the use ceiling are
  the only limits. Revocation would need a table write per grant and has not
  been needed.
